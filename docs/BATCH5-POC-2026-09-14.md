## 0. 结论先行（四条发现）

### 发现 1：D1 在 dsh 内**根本不需要配 key**（推翻原方案）

原方案写的是「独立 key 四通道」（照抄 dsh-tool-writing 的 `DSH_WRITING_API_KEY`）。
但本机把宿主拆开看后确认：**宿主已经把 LLM 能力作为服务开放给插件**。

证据（@deepseek-ai/dsh 内，0.1.5-rc.2）：

| 位置 | 内容 |
|---|---|
| `dsh-llm/lib/types/index.d.ts` | `declare module '@deepseek-ai/cordis' { interface Context { llm: LlmRuntime } }` |
| 同上 | `'llm/stream'` 是 **waterfall** 事件：`(options, next) => AsyncIterable<StreamChunk>`，可拦截 |
| `dsh-agent-default-model` | `ctx.agentDefaultModel` → `{ provider, model }`，即用户已配好的默认路由 |
| `dsh-session-title-llm` | **宿主内已有同款消费者**：253 行，插件身份调 `ctx.llm.stream` 生成会话标题 —— 可直接当模板 |

所以 dsh 内的 D1 = **复用用户已配的 provider/model**，零新增配置。
只有 **MCP 独立模式**（`mcp/server.mjs`，跑在 Claude Desktop / Cursor 里，没有宿主）才需要真·独立 key + 裸 HTTP。

> 影响：D1 从「重资产（要配 key）」降为「中资产（要处理流式与错误）」。
> 剩下的"重"只有一处：**宿主的重试策略不覆盖旁路调用**（见 §1.4）。

### 发现 2：「四通道」不能用 `purpose` 实现

`GenerateOptions.purpose` 是**封闭联合**：`'compaction' | 'session-title'`（types.d.ts:443）。
它表示「宿主的两种辅助调用」，不是给插件分类用的。通道分离只能在**本插件自己的配置层**做：

```
engine.channels = { polish: {...}, draft: {...}, sync: {...}, agent: {...} }
```

每个通道各自带 `provider / model / maxTokens / timeoutMs`，默认全部继承用户当前路由。
真正的账目归因走两条：① 消息级 `source: { kind:'plugin', plugin:'dsh-novel-forge' }`；
② 本插件自己的 `.novel/audit.jsonl` 记通道名与用量。**别指望宿主帮你分流计费。**

### 发现 3：G1 **不能**复用 `ctx.llm` 做 embedding

`ModelModalityMap` 只有两个成员：`text` | `image`（types.d.ts:187-192）。
**没有 embedding 模态** —— 宿主的 LLM 服务是对话/流式服务，不提供向量能力。
含义：真语义检索必须**自带 embedding 通道**（另配一个 provider），这是货真价实的新配置项。
→ G1 的路线选择因此变成「本地词法 vs 云 embedding vs LLM 打标」的取舍（见 §3）。

### 发现 4：`node:sqlite` 可用 → G1 零依赖（但要自己做中文分词）

| 运行时 | `node:sqlite` | SQLite 版本 |
|---|---|---|
| Node 22.22.2（managed） | ✅ 可用，**无需 flag**（仅 ExperimentalWarning） | 3.51.2 |
| Node 26.8.2（system） | ✅ 可用，无需 flag | 3.53.4 |

`FTS5` 与 `json1` 均编译在内。**不需要 `better-sqlite3`**（免原生编译、免预编译包镜像问题）。
但 FTS5 的中文分词**必须自己解决**（见 §3.1 实测）。

## 1. D1 · 旁路直调

### 1.1 现状与痛点

`lib/server-api.js` 里有两个 **501 桩**：

| 行 | 端点 | 现在的行为 |
|---|---|---|
| 425 | `POST /projects/:id/chapters/:no/write` | `501 NOT_IMPLEMENTED`「一键写章需要模型参与，请在聊天中调用 novel_write_chapter」 |
| 433 | `POST /projects/:id/chapters/:no/polish` | `501 NOT_IMPLEMENTED`「一键润色需要模型参与，请在聊天中调用 novel_polish」 |

后果有三：
1. **面板永远是半个摆设** —— 听书、看稿、审稿指标能用，唯独"动手"的按钮不能用；
2. **内部工序占主上下文**：校对/蒸馏这类反复往返的活，把主对话窗口塞满，也烧主额度；
3. **历史被污染**：读会话历史时会看到一堆「这里改成 X」的校对往返，与创作主线混在一起。

### 1.2 两条传输后端（PoC 只做第一条）

| 后端 | 机制 | 适用 | 配置成本 |
|---|---|---|---|
| **A · hostLlm** | `ctx.llm.stream(...)` | dsh 插件运行时（主场景） | **零** |
| **B · directHttp** | 裸 fetch + 独立 key | MCP 独立模式（无宿主）、跨 provider 分流 | 需用户配 key |

接口设计（让后端可换，PoC 不锁死）：

```
lib/engine.js
  createEngine(ctx, config) → {
    channels,                                  // 通道配置表
    run(channel, { system, messages, maxTokens, timeoutMs, signal }) 
      → { text, finish, usage }                // 统一出口
  }
```

后端 A 走 `ctx.llm`，后端 B 走 `globalThis.fetch`。**PoC 只实现 A**；
B 留到「要跑 MCP 独立模式」或「要跨 provider 分流」时再加（接口留好即可）。

### 1.3 调用契约（照宿主内模板写，别自己发明）

```js
import { BlockAssembler, createUserMessage } from '@deepseek-ai/dsh-llm';

const messages = [createUserMessage({
  content: [{ type: 'text', text: framedInput }],
  source: { kind: 'plugin', plugin: 'dsh-novel-forge' },   // 消息级归因
})];

const options = deepFreeze({
  provider, model,                    // 取自 config.channels[x] 或 ctx.agentDefaultModel
  messages, system,
  maxTokens, sessionId, signal,
});

const assembler = new BlockAssembler();
for await (const chunk of ctx.llm.stream(options)) assembler.push(chunk);

// assembler.finish.kind ∈ 'stop' | 'error' | 'aborted' | 'max-tokens' | 'tool-calls'
// assembler.blocks() → [{ type: 'text', text }, ...]
```

**插件侧要动的注入**：`lib/index.js` 的

```js
export const inject = ['tools', 'fs', 'systemPrompt'];   // → 加 'llm'
```

⚠️ 注意 cordis 的 `inject` **只有必选、没有可选**：
`Inject = (keyof M)[] | { [K]: intercept-config }`（`cordis/lib/types/registry.d.ts:13`）——
对象形态是**拦截配置**，不是 `{ required, optional }`。
所以引擎必须在**调用时自检** `ctx.llm` 是否存在，缺失就退回今天的 501 文案。
（dsh 里 `llm` 是核心服务，实际不会缺；这条是给 MCP 独立模式与未来宿主版本留的门。）

### 1.4 「重」在哪：流式与错误（这是 PoC 的核心工作量）

**① 宿主不给旁路调用重试。**
`dsh-llm-retry` 的类型头写得明确：*"Provider-routed model-request retry policy on the
agent loop's request recovery extension point"* —— 它挂在**agent loop 的请求恢复点**上，
手搓的旁路调用**不吃这套**。engine 必须自带：

- 超时：用宿主的 `deadline(signal, ms, CODE)`（`@deepseek-ai/dsh-timeout`），上限 `MAX_TIMER_DELAY_MS`；
- 重试：指数退避 + 抖动，只对可重试类（网络/429/5xx）重试，**上限 2 次**；
- 按 `finish.kind` 分流，不能一律重试：

| `finish.kind` | 正确处置 |
|---|---|
| `stop` | 正常 |
| `max-tokens` | **拆批重跑**（输出被截断，重试同样截断） |
| `aborted` | 直接放弃（用户取消 / 超时） |
| `error` | 按 `failure.code` 判可重试性（`AUTH` 重试无意义） |
| `tool-calls` | 纯文本工序视作**异常**（模型跑偏了） |

**② 流式必须增量收集。** 润色是长输出，必须 `for await` 边收边拼（`BlockAssembler`），
不能等整串。要不要边流边 SSE 推给面板，是 PoC 的加分项，**不是必需**。

**③ 可取消。** 面板关闭 / 用户反悔 → `AbortSignal` 贯穿到底，
否则会留下一个"孤儿请求"占着额度。

### 1.5 PoC 范围：只动 `/polish` 与 `/proofread`

| 端点 | PoC 做什么 | 不做什么 |
|---|---|---|
| `/polish` | 把 `novel_polish` 的「生成修改提案」搬进引擎跑（**提案制不变**：引擎出提案 → 落盘 → 用户在面板点「应用」） | 不让引擎直接落盘改正文 |
| `/proofread` | 机械校对（错别字/标点/易混字）走引擎 + 复用已有的 `validatePolishEdits` 守卫 | 不扩到文学性润色 |
| `/write` | **不进 PoC** | 写章要 `briefing` 上下文包 + 内容门禁 + 账本落账，塞进旁路等于把整套工作流搬进 engine |

> 为什么写章不能顺手做：写章不是"一次模型调用"，是「取上下文包 → 生成 → 门禁四维 → 账本落账 →
> 机审 → 版本落盘」的流水线。搬进旁路等于重写一遍主链路，且会绕开第三/四批刚建好的保护。

### 1.6 验收 / 终止条件

验收（四条全过才算成）：

1. 面板点「一键润色」**端到端出提案**（不是 501）；
2. **会话历史不出现内部工序往返** —— 对比 PoC 前后同等工作量的 session 消息数；
3. 断网 / 超时 / 401 三种错误各回一条**人话**错误，面板不挂（给可读 code + 建议）；
4. `npm test` 全绿（引擎注入假 llm 测试，不让测试打真网络）。

**终止（不做全量）**：若第 2 条做不到 —— 即 `ctx.llm.stream` 带 `sessionId` 会把请求写进
会话日志、导致历史仍被污染 —— 则 D1 的核心价值（省主上下文）不成立，
降级为「只在 MCP 独立模式提供」或直接搁置。
**这是 PoC 的第一个实验，应该最先跑。**

## 2. D2 · 并发批量起草

### 2.1 先选路：两条实现，代价差一个量级

| 路线 | 机制 | 能力 | 代价 |
|---|---|---|---|
| **A · `ctx.subagents`** | 宿主有 `ctx.subagents.start(...)`（provider：spawn-in-process / fork / acp），起**真子代理** | 有工具、有独立上下文，能自己查账本、跑门禁 | 每个子代理 = 一整轮 agent，贵 |
| **B · `ctx.llm` 裸并发** | 复用 D1 的 engine，一次调用出一章草稿 | 无工具、无门禁，产物是"裸稿" | 便宜、快 |

**建议 PoC 走 B**（D1 已把 engine 建好，复用即得），子代理路线留给「需要工具的重活」。
裸稿必须由主流程再过 `content-gate` + 账本 —— 即 **并发生成、串行提交**。

### 2.2 四个硬约束（并发写章的坑）

1. **账本必须串行落账。** 章节文件按章号命名、互不覆盖，可以并行写；
   但 `facts_updates` 并发写同一章会互相覆盖（`novel_ledger` 的同章键冲突检查会拒）。
   做法：**并发生成 → 逐章串行提交**。
2. **上下文预算 × N。** N 章并发 = N 份 `briefing` 上下文包同时在场。
   默认 `concurrency: 1`；用户显式开到 2–4，**上限 4**；
   并且**只在有场景契约（第三批 B3）裁过上下文的书上放开**——第三批的收益在这里兑现。
3. **顺序依赖。** 第 N+1 章依赖第 N 章结尾。真正的做法是**先把 N 章细纲都出了**，再并发起草；
   对"连环悬念"的章节**不要并行**（否则后一章会踩前一章没定的伏笔）。
4. **失败不整批回滚。** N 章里 1 章失败，其余照落盘，失败章记审计并在结果里标出。
   整批回滚 = 把已经好的章节扔掉重跑，成本不可接受。

### 2.3 验收

4 章并发起草：① 总耗时 < 串行的 **60%**；② 每章**仍过**内容门禁与机审；
③ 账本无同章冲突；④ 中途 kill 进程 → 已落盘章节完好、索引一致（`novel_project repair` 无异常）。

## 3. G1 · 向量索引（语义检索）

### 3.1 本机实测（不是估计）

| 方案 | 实测结果 |
|---|---|
| FTS5 默认分词器 | 中文 2 字查询 **0 命中**（整段 CJK 被当成一个 token） |
| FTS5 `tokenize='trigram'` | 2 字查询 **0 命中**；**3 字查询也是 0**（实测不可用） |
| FTS5 + **手工二元切分（bigram）** | 2 万块建索引；查询均 **11.0 ms**；索引 **14.4 MB**；BM25 排序正常 |
| `node:sqlite` | Node 22.22.2 / 26.8.2 均可用，SQLite 3.51.2 / 3.53.4 |

**结论**：零依赖路线可行，但**中文切分必须自己做**（bigram）。
代价是索引膨胀（2 万块 ≈ 14 MB；10 万字级长篇 ≈ 20–30 MB，可接受），
`node:sqlite` 是实验特性（有 ExperimentalWarning，跨大版本需回归 → 索引要**可删可重建**）。

### 3.2 三条路线

| 路线 | 召回能力 | 配置成本 | 备注 |
|---|---|---|---|
| **A · 本地词法**（bigram FTS5）+ 结构化信号 | 靠"用户还记得的字面词" | **0**，可离线，11 ms | 叠加已有的账本/伏笔/**人物别名表**能覆盖相当一部分需求 |
| **B · 云 embedding** | 真语义（"救主角那个人"这类无语面重叠的查询才行） | **高**：宿主无 embedding 模态，需另配 provider + 向量存储 + 增量更新 + 阈值调参 | 唯一的"真重资产" |
| **C · LLM 打标**（推荐折中） | 介于 A/B 之间 | 零新增配置（用 D1 的 engine） | 入索引时为每块生成 3–5 个「事件/实体/场景」标签，与正文一起进 FTS5 的 `tags` 列；查询先扩词再检索 |

**推荐 C**：它把"语义"这件事外包给已有的 `ctx.llm`，**不新增任何配置项**，
而且标签是**一次性生成、可增量、可只对未标块跑**（成本可控）。

### 3.3 PoC 范围与验收

范围：
- `novel_search` 增加 `mode: 'lexical' | 'hybrid'`；
- 索引落 `书/.novel/index.db`（SQLite，**派生物**：删库重跑即得，绝不成为真相源）；
- 建索引动作支持**增量**（只处理新增/变更块）；
- **先不动 `novel_briefing` 的注入链路** —— 只让"找一段"可用，不自动往上下文塞内容。

验收（用真实 100+ 章的书跑）：
① 10 个真实检索问题，C 路线命中 **≥ 8**（A 路线作对照，需 ≥ 5）；
② 增量索引：新增 1 章 < **1 s**；
③ 索引损坏可重建（删库重跑，不依赖任何外部服务）；
④ `node:sqlite` 不可用时**优雅降级**到现有关键词检索（不抛错）。

**终止**：若 C 相对 A 的增益 < 20%（量化为 10 题里多命中不到 1 题），
则**不上 embedding、不引入新配置**，只维护 A 路线。

## 4. 建议顺序

```
D1（先做——另两条都要用它的 engine）
   └─> G1（用 D1 的 engine 做 C 路线打标）
          └─> D2（复用 engine；最依赖"上下文预算"这层已有收益）
```

每条 PoC 都能**独立交付**：即使后一条不做，前一条自成收益 ——
D1 = 面板真能用；G1 = 长篇找得回；D2 = 快。

## 5. 明确不做

| 不做 | 原因 |
|---|---|
| 引入 `better-sqlite3` | 原生编译 + 预编译包 + 镜像源三重麻烦；`node:sqlite` 够用 |
| 把 SQLite 变成数据层 | `novel.json` / Markdown 仍是唯一真相；索引是可删的派生物 |
| 为 D1 加"必须配 key 才能启动" | 会毁掉现在的零配置体验；dsh 内本来就不需要 key |
| 用 `purpose` 做通道分流 | 它是封闭联合 `'compaction' \| 'session-title'`，不是插件分类槽 |
| 写章进 D1 PoC | 写章是流水线不是一次调用；搬进旁路会绕开第三/四批的门禁 |

## 6. PoC 开工前的三个待定问题（需要仙尊拍板）

> **已拍板（落地时采纳的默认）**：① D1 通道**全部继承当前路由**（配置可覆盖，但默认零配置）；
> ② D2 并发**默认 1**（上限 4）；③ G1 索引**跟书走** `书/.novel/index.db`。

1. **D1 的通道默认模型**：全部继承当前会话路由（最省事），
   还是允许给 `polish` 通道单独指定一个**便宜模型**（省额度但要配）？
2. **D2 的并发默认值**：默认 1（保守，用户显式开）还是默认 2（体验好但可能吓到人）？
3. **G1 的索引落点**：`书/.novel/index.db`（跟书走）还是全局 `~/.dsh/novel-forge/index.db`（多书共享缓存）？
   建议跟书走 —— 删书即删索引，符合"派生物"定位。

## 7. 落地结果（v0.11.0）

三条全部按本文路线落地，**建议顺序（D1 → G1 → D2）被实际沿用了**，
并且三条都做到了「独立交付」：即使只看其中一条，也是自成收益的完整功能。

| 项 | 落点 | 与本文的差异 |
|---|---|---|
| D1 旁路直调 | `lib/engine.js` + `lib/engine-tasks.js` | 通道名定为 `polish / proofread / annotate / draft`（不是 `sync / agent`）；`attachSession` 默认 false |
| D2 并发批量起草 | `lib/batch-draft.js` + 抽出的 `lib/chapter-commit.js` + `lib/briefing.js` | 多抽了一个 `chapter-commit.js`——门禁链顺序敏感，抄第二遍必然漂移 |
| G1 长篇检索 | `lib/retrieval.js` + `novel_search`（第 19 个工具） | 走**路线 C**（词法 + LLM 标签增强）；标签与正文进**同一检索列** |

**落地时新增的四条经验**（本文没预见到）：

1. **`inject` 没有"可选依赖"**：cordis 的 `inject` 只有必填（对象形式是拦截配置），
   所以引擎改成**调用时自检** `ctx.llm` + 优雅降级。宿主没有 llm 时插件照常装载。
2. **中止要做成真的**：第一版只在循环里查 `signal.aborted`，不听话的适配器照样把
   502ms 超时跑满。改成 `Promise.race` 消费流（且 `iterator.return()` 不能 await——会挂）。
3. **`hitRatio` 必须把标签算进去**：否则 annotate 打好的标签在精度闸门那一步被全丢掉，
   「语义增强」静默失效、看起来像"没效果"。
4. **闸门默认值要靠真实查询调**：0.34 会把「戴斗笠的人」这类只记得一个关键词的
   真实查询全杀掉；0.25 才是能用的值。

**成本复核**：结论与 §0 一致——D1 零配置（复用宿主路由）、D2 零新增配置、
G1 零依赖（`node:sqlite`）+ 可选 token 成本（只有 `annotate` 打标会产生，默认每次 ≤20 块、可分批）。
原方案的「重资产」标签在 PoC 后应改为「**中资产**」。
